# 为什么最终停用网页开发桥接

目标并非只让模型列表多几个名字，而是能在一个长对话里从原生 Astra 切到网页模型继续开发，并避免上下文压缩。

## 三个数字不能混为一谈

1. 模型或产品宣传的上下文窗口。
2. ChatGPT 网页单条消息允许提交的大小。
3. 桥接向 Codex 声明的有效预算和压缩阈值。

在固定的 v5.0.6 实现中，Pro 默认单消息边界为 104000 tokens；加上产品预留得到 context_window=112193，压缩预算为 95000。实验性 Bigger Context 把完整有序记录拆成最多三条消息，窗口成为 336579，压缩预算为 285000。它不是“256k 模型窗口乘三”，更不是接近 900k 的保证。

源码依据：[chatgpt-web-models.ts](https://github.com/miuuyy/codex-chatgpt-web/blob/v5.0.6/src/chatgpt-web-models.ts)、[输入预检](https://github.com/miuuyy/codex-chatgpt-web/blob/v5.0.6/src/adapters/chatgpt-web/browser-worker.ts)。[上游 #76](https://github.com/miuuyy/codex-chatgpt-web/issues/76) 也区分了网页传输边界与模型窗口；该 issue 的旧版本测量不可当作当前账号的实时承诺。

## 为什么不把数字直接写到 900k

Codex 客户端可能因此延后部分压缩，但桥接仍会拒绝超大消息。即使取消本地检查，也没有证明 ChatGPT 会完整接收和保留这些内容。让 UI 显示更大数字，不等于增加真实容量。

本机二进制离线实验还证明，切到较小窗口会在网页执行前触发原生压缩。已有 model_auto_compact_token_limit=900000 不能消除此行为。详见验证记录。

## 调查过但没有冒充已解决的方向

- 上游 [#454](https://github.com/miuuyy/codex-chatgpt-web/pull/454) 提议按套餐设置更大窗口，但关闭且未合并，也没有建立 900k 完整直传证据。
- 上游 [#471](https://github.com/miuuyy/codex-chatgpt-web/issues/471) 提议通过 MCP 分块读取上下文，重点是减少输入框传输负担。能分块搬运文本，不等于远端模型能同时保留 900k 全量上下文；其小规模实验也不能证明这一点。
- 将原文放入文件并按需检索，可以保留资料，却不是“同一模型一次完整看到全部历史”。

## 最终取舍

这条路径适合可独立验证的小任务，也确实提供了订阅额度的备用开发通道。但对于“长会话无压缩互切”的核心需求，目前的证据不够，使用体验和恢复成本不符合预期，因此退役而非继续堆高声明容量。

保留代码和失败记录，用于其他使用者判断；本机原生 Codex 配置恢复。后续采用不同分工：网页通过只读 MCP 按需了解项目和本地资料，负责规划；原生 Codex 执行开发。这不要求网页承接整个原生 900k 历史，也不能被描述成两者上下文容量已经相同。

## 最终本地清理核验

退役后重新用桌面随附 app-server 读取模型目录，只有五个原生模型。旧应用、私有桥接配置目录、命令、具名 profile 和启动项已移除，旧环回端口没有监听。原 model_provider=custom、原生 Astra，以及用户保留的 1000000 窗口/900000 压缩阈值均保留；没有留下 model_catalog_json 或旧桥接 base URL。

只读规划 MCP 已明确拆分到独立工作区和任务，用户要求只在本地开发、不提交 GitHub。本公开仓库仅包含旧桥接的历史经验和实验工具，不包含只读 MCP 的实现或私有运行配置。

## 正式归档

2026-09-16，使用者确认本项目探索结束。本仓库及旧私有实验仓库停止开发；本机只保留原创适配、结论和压缩后的必要证据，移除可重新下载的上游源码副本、依赖、构建/临时缓存和克隆历史。安装入口、更新与产品归属仍指向原作者。独立只读 MCP 项目不在本次归档或清理范围内。
